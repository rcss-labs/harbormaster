# Backup and restore

Postgres is Harbormaster's source of truth, and one secret, `HM_SESSION_KEY`, protects data inside it. This page explains what to back up, which key you must keep, what the Terraform module already protects and what to check after a restore. It is for operators who own recovery.

!!! note "What is verified"
    This page describes what the code and the Terraform module do. A restore procedure for your environment, and its timing, are yours to rehearse. Items marked TODO could not be verified from the repository.

## What holds state

| Component | Holds | Back it up? |
| --- | --- | --- |
| Postgres (RDS) | Users, permissions, tags, sessions, snapshots, alerts, settings, the audit log, operations log, notification routes and queue, leases, hashed access tokens, SSO configuration and sealed keys | Yes. This is the truth |
| `HM_SESSION_KEY` (Secrets Manager `harbormaster/session-key`) | The key that seals secrets stored in Postgres | Yes. See below |
| Valkey or Redis | Open pages, signals, shared limits and cached read models. Every key expires | No. Disposable. A new empty store is safe |
| Your AWS accounts | The ECS, ECR, CloudWatch and EFS data that Harbormaster reads | Not Harbormaster's job. Harbormaster does not copy it |
| Terraform state | The module's resources and the generated database password and session key | Yes, in your deployment system |

Harbormaster re-reads AWS state continuously. After a restore, snapshots (clusters, services, tasks) refill from the first polls, so recovery only needs the configuration and history that Harbormaster itself owns.

## The key you must keep: HM_SESSION_KEY

`HM_SESSION_KEY` is used for three things:

| Use | Mechanism | If the key changes or is lost |
| --- | --- | --- |
| Session ID hashes | Session IDs are hashed together with the key | Every existing session stops working. Users sign in again. Nothing else is lost |
| SSO service-provider private key | Sealed at rest with AES-256-GCM under a key derived from `HM_SESSION_KEY` | The key cannot be decrypted. The SSO settings page shows `The service provider key cannot be decrypted. Check HM_SESSION_KEY or generate a new certificate.` Sign-in through SSO fails until you generate a new certificate and update the identity provider |
| Notification route secrets (webhook URLs, tokens, passwords) | Sealed with AES-256-GCM under a key derived from `HM_SESSION_KEY` and bound to the purpose `harbormaster/notify-secret/v1` | Deliveries on routes with a secret fail with the note `Enter the destination again.` Re-enter the destination of each affected route |

Access tokens and OAuth grants are stored as hashes without this key and are not affected.

Rules for the key:

- Keep the same value for the life of the install. Restore it with the database.
- With the Terraform module, the key is generated by `random_id` and stored in the secret `harbormaster/session-key`. The value also lives in Terraform state. Back up the state in your deployment system, and do not delete the secret by hand. If the state is lost and the module re-creates the key, treat it as a key loss.
- Never print the key or paste it into a ticket. Read it only when you restore it into a new secret.
- Rotating the key is a deliberate action with the effects in the table. There is no in-place re-encryption command. <!-- TODO(docs): confirm with maintainers that no key-rotation or re-seal procedure exists; none was found in cmd/harbormaster or internal/secretbox. -->

## What the Terraform module protects

| Setting | Default | Variable |
| --- | --- | --- |
| Automated RDS backups | 7 days of retention (fixed in the module) | none |
| Final snapshot on destroy | Taken, named `harbormaster-final` | none |
| Deletion protection | On | `db_deletion_protection` |
| Storage encryption | On, with `db_kms_key_id` or the AWS managed key | `db_kms_key_id` |
| Multi-AZ | Off | `db_multi_az` |
| Tags copied to snapshots | On | none |

Secrets Manager secrets (`database-url`, `session-key`, `metrics-token`, and `kv-url` for a created cache) use the default 30-day recovery window when deleted.

Add what the module does not do:

- If 7 days is too short for your recovery needs, take manual snapshots or use AWS Backup. <!-- TODO(docs): the module fixes backup_retention_period at 7 and has no variable for it. Confirm the recommended way to extend it. -->
- Copy snapshots to a second region or account if you need protection from a regional loss.
- Turn on `db_multi_az` if a database failover must not interrupt service. A failover drops connections. The tasks reconnect, and `/healthz` fails while the database is unreachable.

## Back up

1. Rely on automated RDS backups for point-in-time recovery inside the retention window.
2. Take a manual snapshot before an upgrade or a risky change:

    ```sh
    aws rds create-db-snapshot \
      --db-instance-identifier harbormaster \
      --db-snapshot-identifier harbormaster-before-<change> \
      --profile <profile> --region <region>
    ```

3. Keep the Terraform state and the `harbormaster/session-key` secret in your normal backup process. Restoring the database without the key loses the sealed values.

## Restore

Restoring creates a new database instance. Plan for a short outage.

1. Choose the snapshot or the point in time. Restore it to a new RDS instance with the same engine version, subnet group and security group as the original.
2. Make sure the secret `harbormaster/database-url` holds a URL that points at the restored instance, with the same credentials. The restored database carries the old user and password.
3. Make sure `harbormaster/session-key` holds the original key.
4. Stop or scale down the Harbormaster tasks, so no task writes to the new database while you switch.
5. Point the install at the restored database. With the Terraform module, import or replace the instance in your deployment system and apply there. Run plan and apply with your usual Terraform workflow.
6. Start the tasks. Each task applies any pending migrations at start. Migrations are forward-only and additive, so a snapshot taken on an older version is brought up to the running version. <!-- TODO(docs): verify that running an older image against a newer schema is unsupported or safe; no down migrations exist in internal/store/migrations. -->
7. Wait one lease cycle (up to 35 seconds) for pollers to claim slices.

### Check it worked

- `/healthz` answers `200` on every task.
- You can sign in. If you cannot, create a break-glass administrator with the command below, run in the same environment as the server (it needs the database settings):

    ```sh
    harbormaster create-admin --username <name> --password-stdin
    ```

    The new administrator must change the password at first sign-in. It also works while SSO is on.
- The sum of `harbormaster_lease_slices_owned` over all pollers equals the number of enabled account and region pairs.
- The AWS accounts page shows no stale banner after a few minutes.
- SSO settings do not show the "cannot be decrypted" warning, and a notification test send works.

### What a restore loses

Everything written after the snapshot or the chosen point in time: new users, setting changes, audit and operations log entries and tags. Snapshots of ECS state are rebuilt by polling. Stale rows for clusters or services that changed in the gap are replaced on the next poll.

If you restored to a time before an access token was revoked, the token works again. After a restore from an old snapshot following an incident, run `harbormaster revoke-tokens --all`.

## Account connections after a restore

Each connected account is a row in the database that holds the role ARN and the external ID. The external ID is also part of the trust policy in the target account. A restore from a snapshot that predates a connected account loses that account's row.
