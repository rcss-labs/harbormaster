# Harbormaster 07: SAML SSO Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add SAML 2.0 single sign-on (SP-initiated, single IdP, JIT user creation with no permissions) configured entirely from the Settings page, with break-glass password accounts, lockout guards, an in-repo fake IdP for tests and demos, and no change in behaviour for installations that never configure it.

**Architecture:** One new Go package, `internal/saml`, owns everything SAML: SP key generation and at-rest encryption, IdP metadata parsing and safe fetching, SP metadata rendering, AuthnRequest building, and a `Verifier` that wraps `github.com/crewjam/saml`'s `ServiceProvider.ParseXMLResponse` and then independently re-checks every rule in the spec's validation table. `internal/saml/fakeidp` is a tiny IdP on crewjam's `saml.IdentityProvider` used by Go tests, Playwright and `serve --fake-aws`. Request state and the replay cache are Postgres rows (`saml_requests`, `saml_assertion_ids`) so any ECS task can serve any step; a `hm_saml_req` binding cookie adds login-CSRF defence. `internal/auth` gains `LoginSSO`/`PreviewSSO`/`StartLink`/`LinkSSO`, break-glass enforcement in `Login`, and `not_after` on sessions. Users carry two independent credentials (password, SSO identity) plus an admin-set pending link (spec D6/D11); the request row has a `purpose` (`login`, `test`, `link`). `internal/api` adds four public routes (`/api/auth/options`, `/api/auth/saml/{login,acs,metadata}`), the authenticated `POST /api/auth/saml/link`, the admin `/api/sso*` routes and the per-user link/unlink/pending-link routes; the ACS is the one new CSRF-exempt POST and it never reads the session cookie. The SPA adds the SSO button and break-glass link to Login, a "Single sign-on" Settings tab, a "Link SSO account" dialog in the sidebar footer, and sign-in/break-glass/link controls on Users.

**Tech Stack:** Go 1.26 (module says `go 1.27.3`; keep whatever `go.mod` says), `github.com/crewjam/saml v0.5.1` + `github.com/russellhaering/goxmldsig v1.6.1` (direct require), pgx v5, `net/http` ServeMux; React 19 + TypeScript, react-router, TanStack Query v5, CSS modules, Vitest + Testing Library + MSW, Playwright.

**Spec:** [`docs/superpowers/specs/2026-11-02-saml-sso-design.md`](../specs/2026-11-02-saml-sso-design.md) (binding: decisions D1–D10, the validation table, the API table, the UI copy, the audit table). **Conventions:** [`2026-10-31-00-conventions.md`](2026-10-31-00-conventions.md) applies in full.

## Decisions (rulings the implementer must not re-decide)

1. **Package layout:** `internal/saml` (pure logic, no store import), `internal/saml/fakeidp` (test IdP), `internal/auth` (sign-in semantics, imports `internal/saml` for `Identity`), `internal/api/saml_public.go` + `saml_admin.go` (HTTP). The store knows nothing about XML.
2. **`store.User.PasswordHash` stays `string`**; the select uses `coalesce(password_hash, '')`. Empty string means "no password". `Login` treats it like an unknown user (dummy verify, generic error). `store.CreateSAMLUser` writes NULL. There is **no `auth_source` column on users** (spec D6); `UserDTO.sso` is derived in `buildUserDTOs` from `ExternalID`, `PendingLinkNameID` and `PendingLinkExpiresAt` vs `s.now()`.
3. **Request IDs** are `"_" + hex(32 random bytes)` (SAML IDs must start with a letter or underscore). The same string is `AuthnRequest/@ID`, `saml_requests.id` and `RelayState`. `saml_requests.purpose ∈ {login, test, link}`; `user_id` is set only for `link`.
4. **Binding cookie** `hm_saml_req`: `Path=/api/auth/saml/acs`, `HttpOnly`, `Max-Age = HM_SAML_REQUEST_TTL`, `SameSite=None; Secure` when `cfg.CookieSecure`, else `SameSite=Lax`. Cleared (Max-Age −1) on every ACS response. The row stores `hex(sha256(value))`.
5. **Enable guard, last-break-glass guard** live in `store` transactions that take `lockAdminsTx` first (`for update` on admin rows) and read `saml_config.enabled` inside the same transaction. Errors: `store.ErrNoBreakGlassAdmin` (enable), `store.ErrLastBreakGlassAdmin` (revoke/demote/delete), `store.ErrNeedsPassword` (break-glass on a password-less user), `store.ErrAlreadyLinked`, `store.ErrSSOIdentityTaken`, `store.ErrNotLinked`. `api.fail` maps the first three to 422 `invalid` with the spec's messages, `ErrAlreadyLinked` → 409 `already_linked`, `ErrSSOIdentityTaken` → 409 `sso_identity_taken`, `ErrNotLinked` → 404.
6. **Session deletion on config change** happens inside `UpsertSAMLConfig`/`SetSAMLEnabled` transactions (`delete from sessions where auth_source = 'saml'`), decided by the store from old vs new row: entity ID changed, or any previously stored certificate fingerprint missing from the new set, or `enabled` true → false. An entity ID change also nulls every user's identity and pending-link columns (spec D6 rule 7). **No store write ever nulls `password_hash`** except `UnlinkSSO` setting a temporary one (owner decision 7: passwords are never cleared).
7. **Test flow** reuses `saml_requests`: the ACS consumes the row (`DELETE … RETURNING`), and for `purpose = 'test'` re-inserts it with `result` set and `expires_at = now + 10 min`; `TakeSAMLTestResult` is a `DELETE … RETURNING result`. No separate table.
7a. **Link flow** (spec D11): `POST /api/auth/saml/link` is a normal protected route (`RequireAuth`, `RequirePasswordChanged`, `RequireCSRF`), verifies the password with `auth.Service.StartLink`, and creates a `purpose = 'link'` row with `user_id`. The ACS branches on `purpose`: `login` → `auth.LoginSSO` (linked → pending → JIT), `test` → preview, `link` → `auth.LinkSSO(ctx, row.UserID, identity, cfg)`; link outcomes redirect to `/?sso_link=ok|{reason}` and never set a session cookie. `store.BindSSOIdentity` is one transaction that re-checks uniqueness (the partial unique index) and never touches `password_hash`.
8. **Rate limits:** `GET /api/auth/saml/login` uses a new `internal/api/ratelimit.go` per-IP token bucket (60 tokens, refill 1/s, in-process; `429 rate_limited`, a new code: the existing `throttled` is the 503 "AWS is throttling us"). ACS failures call `store.RecordLoginAttempt(ctx, "sso:"+ip, ip, false)` so `FailedAttempts` by IP (existing `LoginMaxPerIP`) also blocks the ACS; the precheck runs before any XML parsing.
9. **Username derivation** is `saml.DeriveUsername(id Identity, cfg Config, taken func(string) bool) string` (pure); `auth.LoginSSO` supplies `taken` from `GetUserByUsername`. Suffix `-2`…`-99`; beyond that, reason `user_create_failed`.
10. **Well-known attribute names** (used when the configured name is empty), in order: email → `email`, `mail`, `emailAddress`, `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress`, `urn:oid:0.9.2342.19200300.100.1.3`; display name → `displayName`, `name`, `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/name`, `http://schemas.microsoft.com/identity/claims/displayname`, `urn:oid:2.16.840.1.113730.3.1.241`. Attributes are matched by `Name`, then by `FriendlyName`.
11. **Fake IdP** lives at `/fake-idp/metadata`, `/fake-idp/sso`, `/fake-idp/submit.js`; its signing key pair is generated at construction (deterministic from a seed for golden-free tests is not required); IdP entity ID `http://127.0.0.1:<port>/fake-idp` (whatever base URL it is given). Users are any `^[a-z][a-z0-9.-]*$` name; NameID `{user}@example.test`, attributes `email={user}@example.test`, `displayName={User}` (capitalised), `givenName`, `sn`.
12. **The SPA's `login()` e2e helper** clicks `Sign in with a password instead` when visible, then proceeds as before; no other spec changes.
13. **Model tiers** per task are in each heading; Opus reviews each task and runs Task 18. Escalate per CLAUDE.md when stuck.

## Review Focus

Inputs the spec implies but a casual implementation misses; each has its pinning test.

1. A response with a valid signature for **another SP** at the same IdP (different audience, our ACS as destination) must fail → Task 7 `TestVerify_RejectsForeignAudience`.
2. A response whose **`Response` is signed but carries two `Assertion`s** must fail even if the first is fine → Task 7 `TestVerify_RejectsMultipleAssertions`.
3. **The same ACS POST sent to two servers over one store** must produce exactly one session → Task 9 `TestACS_TwoServersOneStore_OnlyOneSessionWins`.
4. **Turning SSO on with zero break-glass admins** must fail even when the request races a break-glass revoke → Task 3 `TestSetSAMLEnabled_ConcurrentRevokeAndEnable_OneFails`.
5. A **non-break-glass local user with the right password** while SSO is on gets 403 `sso_required`, is audited, and gets no cookie → Task 8 `TestLogin_SSOOnRequiresBreakGlass`.
6. **`return_to` of `//evil.example`, `https://evil.example`, `/\evil.example`** all collapse to `/` → Task 9 `TestSAMLLogin_ReturnToIsRelativeOnly`.
7. **Metadata URL `http://169.254.170.2/…`** is refused in production mode even when the DNS name resolves to it indirectly → Task 5 `TestMetadataFetcher_BlocksLinkLocalAndPrivate`.
8. **Disabling SSO** ends SAML sessions but not password sessions; the admin who disabled it stays signed in → Task 3 `TestSetSAMLEnabled_DisableEndsOnlySAMLSessions`.
9. **An existing e2e run** with SSO never configured produces identical behaviour: `GET /api/auth/options` returns `sso: null` and the login page renders exactly the old form → Task 13 `Login.test.tsx` "renders the password form when SSO is not configured" and Task 18's full suite.
10. **A link started by user A, completed with an assertion for an identity already linked to user B**, must fail with `sso_identity_taken` and leave B untouched; and two concurrent self-links for the same identity must yield exactly one link → Task 8 `TestLinkSSO_IdentityTakenAndConcurrent`.
11. **A cross-site `GET` cannot start a link flow** (`GET /api/auth/saml/link` → 405) and a `POST` without the CSRF header → 403 `csrf`; a wrong password → 401 and no `saml_requests` row → Task 9 `TestSAMLLink_StartRequiresCSRFAndPassword`.
12. **Linking and enabling never touch passwords**: a linked user still signs in with the password while SSO is off, is refused with `sso_required` while it is on (unless break-glass), and signs in with it again after SSO is turned off → Task 8 `TestLinkSSO_PasswordUntouched_SignInGatedBySSOState` and Task 4 `TestSetSAMLEnabled_NeverTouchesPasswords`.
13. **An expired pending link is ignored** (sign-in JIT-creates instead of binding) and **a pending NameID cannot be set on two users** → Task 3 `TestPendingLink_ExpiryAndUniqueness`, Task 8 `TestLoginSSO_ExpiredPendingLinkFallsBackToJIT`.
