# Harbormaster 02: Change (task definitions and operations) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a permitted user edit a service's task definition, register a revision, deploy or roll back any revision, restart a service, change its desired count and stop a task, with every action written to the operations log and the rollout visible on the service page.

**Architecture:** A new `internal/deploy` package holds all change logic behind pure, table-tested functions (describe→register-ready conversion, validation, controller gating) and a `deploy.Service` that talks to AWS through `awsx` and records attribution in Postgres. `internal/api` adds the spec §13 change endpoints with per-action permission checks. The frontend adds the Task definition tab, the header dialogs, the Tasks-tab Stop action and the rollout card; rollout completion toasts are detected client-side from the 5 s service poll, while a server-side `OutcomeLogger` closes `deployment_history` rows and writes the outcome to the operations log. The AWS fake simulates rollouts (including the mockup's OOM failure and circuit-breaker rollback) so `make run` and e2e demonstrate the whole flow.

**Tech Stack:** Go 1.26, AWS SDK for Go v2 (`ecs`, `ecr`), pgx v5, net/http ServeMux; React 19 + TypeScript + TanStack Query v5, Vitest + Testing Library, Playwright.

**Spec:** `docs/design/2026-10-31-harbormaster-design.md` — §7 (all), §6.4 Task definition tab, Tasks-tab actions, Overview rollout card, §13 change endpoints, §12 `revision_records` / `deployment_history` / `operation_log`. Shared conventions: `docs/superpowers/plans/2026-10-31-00-conventions.md` (read first). Mockup: `docs/design/mockup/index.html`; screenshots `docs/design/screens/service-task-definition.png`, `service-overview.png`, `service-tasks.png`.

## Global Constraints

- Everything in plan 00 "Global constraints" applies (Go 1.26, module `github.com/rcss-labs/harbormaster`, SDK v2, pgx v5, slog, ServeMux patterns, React 19/Vite/TanStack v5, MIT, no Stackstead code, `HM_` env config, all AWS via `internal/awsx` interfaces, DB tests via `HM_TEST_DATABASE_URL`, verbatim spec copy, full-width layout, conventional commits, TDD, `gofmt -l cmd internal` / `go vet ./...` / `npm --prefix web run lint` / `npm --prefix web run typecheck` before every commit).
- Register-ready conversion removes exactly: `taskDefinitionArn`, `revision`, `status`, `requiresAttributes`, `compatibilities`, `registeredAt`, `registeredBy`, `deregisteredAt`; everything else is kept (§7.1).
- AWS resource tags of the deployed task definition (`ListTagsForResource`) are copied to the new revision (§7.1).
- Non-admins may not change `taskRoleArn` / `executionRoleArn`: "Changing roles needs a global admin". `secrets` changes by non-admins only when the new ARN is in the service's account and its name keeps the prefix of an existing `secrets` reference in the deployed revision (§7.1).
- Changing `family` is rejected: "Use Terraform to create a new family". At least one essential container. Fargate CPU/memory combination must be valid (§7.1). AWS's own validation error is shown verbatim.
- Deploy/rollback/restart are refused while a deployment is `IN_PROGRESS`: "A rollout is already running" (§7.3). The server re-reads the service with `DescribeServices` before `UpdateService`, never from the snapshot.
- Services with `deploymentController.type` `CODE_DEPLOY` or `EXTERNAL`, or `deploymentConfiguration.strategy` `BLUE_GREEN`: Deploy, Restart and Roll back disabled with "This service is deployed by *{name}*. Harbormaster shows it but can't deploy it yet." Registering revisions and desired count still work (§7.3).
- Desired count 0–`HM_MAX_DESIRED_COUNT` (default **50**) with an auto scaling range warning (§7.3).
- Stop task reason: `Stopped by <username> via Harbormaster` (§7.3).
- ECR tags: only for images in the **same account** as the service; cached **60 s**; otherwise a free-text tag field (§5.1). `ListTaskDefinitions` cached **30 s** (§5.1).
- Revisions registered without a `revision_records` row are shown as registered by "terraform" (§6.4).
- Main container = container whose `name` equals the service name, else the first `essential` container (§6.4).
- Every action is written to `operation_log` with `source = 'harbormaster'` and the actor (§6.4, §7.2).
- Permission letters: register **E**, deploy/rollback **D**, restart / desired count / stop **O**. No View on the effective tag ⇒ 404 `not_found`; View without the action ⇒ 403 `forbidden` via 01's `forbiddenAction(w, action, tagName)` (00 §api: `forbidden` covers admin areas and a visible resource whose action is missing).
- Deployment strategy, circuit breaker and alarms are shown, never changed (§7.3).

### Task 3: Fake rollout simulation (UpdateService, Advance, OOM failure, circuit breaker)

**Implementer:** Sonnet

**Files:**
- Create: `internal/awsx/fake/rollout.go`
- Test: `internal/awsx/fake/rollout_test.go`
- Modify: `internal/awsx/fake/ecs.go` (UpdateService on the scoped client), `cmd/harbormaster/serve.go` (`--fake-aws`: keep the `*fake.Estate` from `fake.MockupEstate(now)` and run `go estate.RunRollouts(ctx, 2400*time.Millisecond)`)

**Interfaces:**
- Produces:
  ```go
  // on 01's target-scoped fake ECS client (fake/ecs.go), mutating the shared Estate under Estate.Mu
  UpdateService(ctx, *ecs.UpdateServiceInput, ...) (*ecs.UpdateServiceOutput, error)
  func (e *Estate) Advance()                          // one simulation step; deterministic for tests (uses e.Now)
  func (e *Estate) RunRollouts(ctx context.Context, step time.Duration) // ticker calling Advance
  ```
  `fake.Service` gains `OOMBelowMiB int` (mockup `oomBelow`: `image-resizer` = 1024, others 0).
- Behaviour, mirroring the mockup's `startDeploy`/`reconcile`:
  - `UpdateService` with `TaskDefinition` or `ForceNewDeployment`: new deployment `id = "ecs-svc/" + 19 digits`, `status PRIMARY`, `rolloutState IN_PROGRESS`, `rolloutStateReason "ECS deployment ecs-svc/… in progress."`, `desiredCount = service desired`, `runningCount 0`, `failedTasks 0`, `createdAt = Now()`; the previous PRIMARY becomes `ACTIVE`; `service.taskDefinition` becomes the target; event `(service X) has started deployment ecs-svc/… for task definition X:N.`. A second `UpdateService` while IN_PROGRESS is allowed by the fake (ECS allows it; the server refuses earlier). `DesiredCount` only: updates `desiredCount` on the service and PRIMARY, no new deployment.
  - Each `Advance()`, per service with an IN_PROGRESS PRIMARY: if the target definition's `memory` < `OOMBelowMiB`: create one STOPPED task on the target revision (`stopCode TaskFailedToStart`, `stoppedReason "OutOfMemoryError: Container killed due to memory usage"`, container exit 137), `failedTasks++`, event `(service X) has stopped 1 running tasks: (task …). Reason: OutOfMemoryError.`; at `failedTasks == 3`: PRIMARY → `rolloutState FAILED`, `rolloutStateReason "ECS deployment circuit breaker: tasks failed to start."`, event `(service X) deployment failed: tasks failed to start. Circuit breaker rolled back to X:<from>.`, then a new PRIMARY deployment for the previous definition (`IN_PROGRESS`, completes on later steps as a normal rollout) and the FAILED one becomes ACTIVE until its tasks are gone. Otherwise: start one RUNNING task on the target (`runningCount++`, event `has started 1 tasks`), stop one task of the old definition if any (`stoppedReason "Scaling activity initiated by (deployment ecs-svc/…)"`, exit 0, event `has stopped 1 running tasks`); when `runningCount == desiredCount` and no old tasks remain: `rolloutState COMPLETED`, reason `"ECS deployment ecs-svc/… completed."`, ACTIVE deployments removed, event `(service X) has reached a steady state.`. Desired count 0 completes on the first step.
  - Per service without a rollout: reconcile running vs desired one task per step (start or stop with reason `Scaling activity initiated by (desired count change)`), `has reached a steady state` when equal; OOM services keep failing (STOPPED exit 137) instead of starting, like the mockup.
  - `notifications` is already seeded mid-rollout `:9 → :10` by 01 (one new task, one old); this task sets its PRIMARY `createdAt = Now() − 3 min` (mockup line 2135) so `Advance()` completes it like any rollout.
